# Deep Audit — 2026-08-19

Seven parallel specialist auditors + one independent Critical Reviewer + lead
verification. Every finding below was verified against code before fixing.

## CRITICAL — fixed

1. **Verify resurrected cancelled bookings / confirmed underpaid amounts**
   `app/api/payment/verify/route.ts` — status checked OUTSIDE the transaction,
   then an unconditional `booking.update({ where: { id } })` committed
   CONFIRMED. A concurrent admin-cancel/expiry-sweep between check and commit
   flipped a CANCELLED booking back to CONFIRMED; a concurrent PUT could shift
   the amount after the (outside-tx) price assert, confirming at a different
   amount than was paid.
   **Fix:** confirmation is now an interactive transaction whose
   `booking.updateMany WHERE status='PENDING' AND totalAmount=payment.amount`
   re-evaluates under the row lock. Loser of any race → count 0 → throw →
   full rollback (payment row never flips to SUCCESS). Covered by
   `tests/unit/payment-guard.test.ts` (6 cases incl. rollback path).

2. **Expiry sweep cancelled bookings mid-checkout**
   `lib/server/expiry.ts` cancelled any PENDING older than 24h — including
   books with a live Razorpay order. Paying customers lost the room, money
   captured, no refund path.
   **Fix:** sweep spares bookings with a live order binding (payment row with
   `razorpayOrderId` updated <24h ago); keyed on `updatedAt` so guest activity
   resets the hold clock. Covered by `tests/integration/expiry.test.ts`
   (real PG: stale / live-order / nulled-binding / fresh).

3. **create-order orphaned paid orders**
   `app/api/payment/create-order/route.ts` unconditionally overwrote
   `razorpayOrderId`. Pay against order A, retry → order B stored → verify(A)
   404 → funds captured, booking stuck PENDING forever.
   **Fix:** idempotent — a live binding is returned as-is; the upsert now runs
   inside a tx with a row-lock "still PENDING" guard; stale (>24h) orders are
   replaced with fresh ones.

4. **Admin cancel raced verify** — `app/api/admin/bookings/[id]` cancelled with
   unconditional update; a paid booking could be silently cancelled (inventory
   released under a paying guest). Now conditional (`WHERE status='PENDING'`),
   with truthfulness re-read on race.
   Same guard applied to user PUT/DELETE (`app/api/bookings/[id]`), which also
   now re-checks `room.isActive` and clears the payment binding atomically with
   the update.

## MAJOR — fixed

5. **Register: no rate limit** — unauthenticated bcrypt cost-10 endpoint =
   CPU/DB DoS amplifier + account-spam pipe. Now IP-limited 5/hour (login
   keeps its tighter per-account gates).
6. **Rate-limit IP spoofing** — `clientIp` trusted the attacker-controlled
   FIRST `x-forwarded-for` entry. Now prefers `x-real-ip`, else the LAST XFF
   entry (the one our proxy appended).
7. **Hold-spam DoS** — recreate PENDING before the 24h sweep → block any
   room's dates forever without paying. Now capped at 3 active PENDING per
   user (409), plus a 365-night max stay (amount-overflow guard).
8. **Zod/malformed-JSON → 500** — admin room input and bad JSON returned
   "Internal Server Error". Now mapped ZodError→400, SyntaxError→400 in the
   central mapper. Covered by `tests/unit/errors.test.ts`.
9. **Homepage without CSP** — middleware matcher excluded public routes;
   now headers on every route (gate logic still /admin-only).

## ROUND 3 (2026-08-19 evening) — capital items closed: webhook + refunds

Supersedes the deferred items below marked (➜ R3). Everything freshly
verified on the final production build.

### Built
- **Razorpay webhook** `app/api/payment/webhook/route.ts` + `lib/server/webhook.ts`:
  HMAC-SHA256 over the RAW body with `RAZORPAY_WEBHOOK_SECRET`
  (timing-safe compare; missing secret → loud 503; bad sig → 401 before any
  DB work). Handlers:
  - `payment.captured` — guarded atomic confirm identical to the client
    verify path (status + amount in WHERE). Raced tx → auto-refund instead
    of stranding the capture. Booking cancelled before capture → refund
    immediately. Booking already CONFIRMED → write the capture in.
    Amount-exactness enforced (partial/tampered captures never confirm);
    unknown order ids acknowledged without state changes; 5xx → Razorpay
    retries, 4xx do not.
  - `payment.failed` — payment → FAILED + order binding cleared (guest can
    retry with a fresh order).
  - `refund.processed` — payment → REFUNDED + booking → CANCELLED (self-heals
    the admin-refund race window). Partial amounts ignored.
- **Admin refund endpoint** `POST /api/admin/refunds`: money move on
  Razorpay first (`payments.refund` — the SDK exposes refund creation there;
  `refunds.create` does not exist in this SDK version), then the local flip
  (booking → CANCELLED, payment → REFUNDED) atomically guarded. Razorpay
  rejection → 502 with zero local changes; raced flip → honest 409.
- **Schema** (migration `20260818203247_payment_refunds`): `PaymentStatus`
  += `REFUNDED`, `payments.refundId TEXT`, booking indexes
  `(userId, createdAt)`, `(roomId)`, `(status, createdAt)` DECLARED in the
  schema — they previously existed only as raw SQL drift (P0 hardening
  migration), so `migrate dev` kept trying to drop them; drift now
  impossible by construction.
- **Seed**: re-seed no longer rotates an existing admin password (prod
  re-runs can't lock ops out); role still enforced; weak/default passwords
  still refused at creation. Old rotating behavior was a review finding.
- **VerifyUser consolidation**: `me` route now uses `verifyUser` (they could
  have drifted); select widened with `name`.
- **intField anti-coercion**: strict `/^\d+$/` — `"0x10"`→16 and `"1e3"`→1000
  no longer slip through (validator gap found in round 1, fixed now).
- **UI**: 8 gratuitous `"use client"` directives removed (amenities,
  experiences, gallery, quote, testimonials, why-choose, room-specs,
  chart-bar — all pure, imported only by server pages); detail-gallery gets
  real alt text (`"<Room> — view N"`); fake `.example` mailto removed from
  booking sidebar; system-map nodes keyboard-operable (role=button,
  tabIndex, Enter/Space, focus ring); auth-provider reads the token via
  `getStoredToken()` (single source — was a third `'vp_token'` literal).
